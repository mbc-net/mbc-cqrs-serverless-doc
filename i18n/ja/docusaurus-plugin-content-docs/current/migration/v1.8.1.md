# 移行ガイド: v1.8.1

v1.8.1 は CLI が生成する Cognito アプリクライアントを修正します。既存プロジェクトでは自分のインフラコードを変更してデプロイする必要があります。npm パッケージの更新だけでは既存ユーザープールは保護されません。

## リリース日

2026-11-25

## 手順 1: アプリクライアントを制限してデプロイ {#app-client-write-attributes}

`infra/libs/infra-stack.ts` の `apigw-client` に次の `writeAttributes` 設定を追加します。ユーザー自身が変更できる属性は `name` のみになります。他のクライアント設定は維持してください。

```ts
const userPoolClient = new cdk.aws_cognito.UserPoolClient(this, 'apigw-client', {
  userPool,
  authFlows: { userPassword: true, userSrp: true },
  writeAttributes: new cdk.aws_cognito.ClientAttributes().withStandardAttributes({
    fullname: true,
  }),
})
```

ECS モード（`config.ecs` を設定）では、サーバー側のユーザー管理に Lambda と同じ Cognito 管理権限を付与するため、既存の `if (!!taskRole)` ブロック内に次の grant も追加します。

```ts
userPool.grant(
  taskRole,
  'cognito-idp:AdminGetUser',
  'cognito-idp:AdminAddUserToGroup',
  'cognito-idp:AdminCreateUser',
  'cognito-idp:AdminDeleteUser',
  'cognito-idp:AdminDisableUser',
  'cognito-idp:AdminEnableUser',
  'cognito-idp:AdminSetUserPassword',
  'cognito-idp:AdminResetUserPassword',
  'cognito-idp:AdminUpdateUserAttributes',
)
```

インフラをデプロイします。アプリクライアントは同じクライアント ID のまま更新され、既存トークンは引き続き有効です。`cdk diff` でクライアントの書き込み属性と ECS ポリシーの変更を確認してください。追加した別のアプリクライアントにも明示的な書き込み許可リストを設定してください。

## 手順 2: デプロイできない場合の一時対処 {#temporary-remediation}

すぐにデプロイできない場合は、対象クライアントの `POOL_ID` と `CLIENT_ID` を設定し、次のコマンドを使用します。`update-user-pool-client` は省略した設定を既定値に戻すため、既存設定をコピーして `WriteAttributes` だけを変更してください。`--write-attributes name` だけで実行しないでください。

```bash
aws cognito-idp describe-user-pool-client --user-pool-id "$POOL_ID" --client-id "$CLIENT_ID" \
  --query UserPoolClient > client.json
jq '{UserPoolId, ClientId, ClientName, RefreshTokenValidity, AccessTokenValidity,
     IdTokenValidity, TokenValidityUnits, ReadAttributes, ExplicitAuthFlows,
     SupportedIdentityProviders, CallbackURLs, LogoutURLs, DefaultRedirectURI,
     AllowedOAuthFlows, AllowedOAuthScopes, AllowedOAuthFlowsUserPoolClient,
     AnalyticsConfiguration, PreventUserExistenceErrors, EnableTokenRevocation,
     EnablePropagateAdditionalUserContextData, AuthSessionValidity, RefreshTokenRotation}
    | with_entries(select(.value != null)) | .WriteAttributes = ["name"]' client.json > update.json
aws cognito-idp update-user-pool-client --cli-input-json file://update.json
```

実行後に `describe-user-pool-client` で確認してください。手順 1 も実施しないと、後の CDK デプロイで古いクライアント設定に戻ります。

## 手順 3: フロントエンドの属性更新を変更 {#frontend-impact}

ユーザーのアクセストークンで更新できるのは `name` のみになります。他の属性に対する直接の `UpdateUserAttributes`（Amplify の `updateUserAttributes` を含む）は `NotAuthorizedException` で失敗します。呼び出し元の権限を確認し、`AdminUpdateUserAttributes` を使用するサーバー側エンドポイントへ移してください。属性の読み取りは変わりません。

## 手順 4: 全ユーザーを監査 {#audit-users}

全ユーザーの `custom:roles`、`custom:tenant`、`custom:groups` および認可に使う他の属性を、アプリケーションの正しい管理情報と照合してください。攻撃者は別テナントの一般ロールを追加したり、グループ所属を変更したりした可能性があります。対象プールの `REGION` と `POOL_ID` を設定してください。

```bash
aws cognito-idp list-users --region "$REGION" --user-pool-id "$POOL_ID" --output json \
  | jq -r '.Users[] | (.Attributes | from_entries) as $a
      | [.Username, $a["custom:tenant"], $a["custom:roles"], $a["custom:groups"]] | @tsv'
```

最近の呼び出しはユーザープールのリージョンの CloudTrail で調べます。イベント履歴は 90 日間で、それ以前のイベントには証跡または CloudTrail Lake が必要です。`START` に ISO 8601 の日時を設定してください。保存されたイベントがないことは、不正利用がなかった証明にはなりません。

```bash
aws cloudtrail lookup-events --region "$REGION" \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateUserAttributes \
  --start-time "$START"
```

Cognito はユーザー名ではなく `sub` を `additionalEventData` に記録し、属性値を隠す場合があります。`list-users --filter "sub = \"<sub>\""` で各 `sub` のユーザーを特定してください。不正な属性を修正し、対象ユーザーに `admin-user-global-sign-out` を実行して更新セッションを失効させてください。発行済みトークンには有効期限まで昇格した権限が残り、グローバルサインアウトだけではオフラインの JWT 検証で拒否されません。

## ローカル開発 {#local-development}

生成される `infra-local/cognito-local/db/clients.json` には `"WriteAttributes": ["name"]` が含まれます。ただし cognito-local 3.23.x はこの設定を強制しません。フロントエンドの属性更新はデプロイ済みの Cognito プールで検証してください。

[変更履歴 v1.8.1](/docs/changelog#v181) と[安全なアプリクライアント設定](/docs/authentication#app-client-write-attributes)も参照してください。
